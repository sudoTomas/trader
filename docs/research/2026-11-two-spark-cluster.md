# A second Spark buys isolation, not intelligence

A second DGX Spark would make almost no difference to trading decisions, memory extraction or embeddings. It would make a real but modest difference to coding agents, and most of that gain comes from giving the coding model its own box, not from clustering the two. Clustering roughly doubles usable memory to about 240 GB. That unlocks the 230-320B "Flash" MoEs (GLM-5.3-Flash, DeepSeek-V4-Flash-0731, MiniMax M2.7). On the one owner-run SWE-bench Pro subset that compares them, those models score 33-38 of 40, against 30 of 40 for Qwen3.8-27B, which fits on one box. On vendor SWE-bench Pro numbers the order flips and Qwen3.8-27B (61.7) beats all of them (52.6-57.9). Clustering does little for speed. Tensor parallelism across the link gives 1.2-1.7x decode on models that already fit one box, and only about 1.17x on 3B-active MoEs like the two the user runs now. The cluster also brings 5-17 minute boots, community-patched images, and no failover when a node drops. On today's single shared Spark, keep **Qwen3.6-35B-A3B** as the coding/agent model. Qwen3.8-27B is a generation better on paper, but at a 25% memory share it gets only about 65K tokens of context and runs at about a quarter of the MoE's speed. **Recommendation:** buying a second Spark mainly for model quality does not pay, because the same money buys roughly 7-8 years of DeepSeek-V4-Flash API usage. Buy one only to end memory contention, and if you do, run the two boxes independently: trading, mem0 and Postgres on one, a dedicated Qwen3.8-27B coding box on the other. Cluster only for occasional runs of a 300B-class model.

## A second Spark mostly buys memory, not tokens per second

The GB10's decode speed is limited by its 273 GB/s of memory bandwidth. Splitting a model across two boxes halves the weight bytes each box reads per token, which sets a theoretical 2x ceiling that measurements never reach. Qwen3-VL-32B AWQ, a dense model, went from **12.36 to 21.11 tok/s (1.71x)** single-stream on two nodes, and its KV pool grew 2.28x ([Techstrong.ai](https://techstrong.ai/features/two-nvidia-dgx-sparks-three-open-models-and-the-benchmark-that-misled-us/)). gpt-oss-120b went from 36 to 55 tok/s on vLLM ([WillItRunAI](https://willitrunai.com/blog/vllm-multi-gpu-setup-guide)). Qwen3.8-Flash-Next NVFP4 gained only **+24.5%** (41.7 to 51.9 tok/s), even though decode used just 0.56 Gb/s of the 200G link ([ai-muninn](https://ai-muninn.com/en/blog/qwen38-flash-next-tp2-two-dgx-sparks)). The model class that matters most here barely moves: Qwen3-30B-A3B NVFP4 went from **64 to 75 tok/s (1.17x)** ([WillItRunAI](https://willitrunai.com/blog/vllm-multi-gpu-setup-guide)). The bottleneck is collective latency, not bandwidth. A small all-reduce costs about **40 µs** against a 2 µs RDMA floor ([Sangiorgi](https://contact.alessandrosangiorgi.net/posts/dgx-spark-nccl-collective-latency/)), and NVIDIA staff confirm GPUDirect RDMA is not supported on GB10 ([NVIDIA forum](https://forums.developer.nvidia.com/t/dgx-spark-gpudirect-rdma/348787)). Each layer pays that latency, so small-active models, where per-token compute is already tiny, gain almost nothing.

Pipeline parallelism does not fix this for single requests. On gpt-oss-120b at batch 1, TP=2 beat PP=2 in every scenario (about 39 vs 29 tok/s). PP=2 pulled ahead only at batch 128, at 555 vs 252 tok/s ([StorageReview](https://www.storagereview.com/review/nvidia-dgx-spark-cluster-review-distributed-inference-on-dell-gigabyte-and-hp)). Unsloth's own guidance from two-Spark testing is to run **two replicas instead of TP** when the model fits one box. Replicas gave 1.30x at 8 users and 1.91x at 32, and one Spark was the better choice below about 8 users ([unsloth PR #10280](https://github.com/unslothai/unsloth/pull/10280)). This user's workload is a handful of streams, so for every model that already fits one Spark, clustering is close to a wash on speed.

The cost is operational, and it is substantial. Multi-node serving in late 2026 runs on community images (eugr/spark-vllm-docker, the bjk110 vllm-spark fork) and per-model sm_121 patches ([eugr/spark-vllm-docker](https://github.com/eugr/spark-vllm-docker)). Owners report many traps. One NGC container's NCCL hangs on GB10, and a plugin falls back to TCP at about 3 GB/s without any warning ([route179](https://route179.dev/2026/07/21/dgx-spark-nccl-roce-benchmarking/)). GLM-5.3-Flash needs strict worker-then-head start ordering, takes 542-608 s to start, and silently corrupts output without `--block-size 2304` ([Classmethod](https://dev.classmethod.jp/en/articles/dgx-spark-2node-glm-5-3-flash-nvfp4-vllm/)). TP=2 does not survive a reboot, `/health` passing does not prove the cluster is serving, and a compile-mode run starved and rebooted both machines ([ai-muninn](https://ai-muninn.com/en/blog/qwen38-flash-next-tp2-two-dgx-sparks)). When one node drops, the whole group dies, and no stack offers degraded-mode failover. For a box that has already frozen once from memory exhaustion, that matters.

## Model scale helps coding by single digits and helps nothing else

Clustering adds memory, and memory only helps workloads whose quality improves with model size. For this user's four workloads, only coding does.

**Trading decide calls.** No evidence shows that a larger local model makes better short structured-JSON trading decisions. StockBench found that financial-QA skill does not carry over to trading ([StockBench](https://arxiv.org/pdf/2510.02209)). A CSI300 study found that frontier agents' returns mostly reflect passive market exposure ([arXiv 2605.28359](https://arxiv.org/html/2605.28359v1)). In Quant-Arena, none of nine frontier models beat equal weight ([arXiv 2610.30113](https://arxiv.org/html/2610.30113v1)). The user's own data is the best signal available: qwen3.8-flash agreed with Grok on 93 of 120 prompts, and local Nemotron 3.5 Lightning on 67. At $0.15/$0.47 per million tokens ([OpenRouter](https://openrouter.ai/qwen/qwen3.8-flash)), each decision costs well under a cent. A cluster also hurts latency. The leading 2-Spark model, DeepSeek-V4-Flash, measured about 5 s TTFT and scored **50% on structured output** with JSON failures in a tool-eval run ([NVIDIA forum](https://forums.developer.nvidia.com/t/deepseek-v4-flash-dspark-on-2x-dgx-spark-gb10-big-single-stream-speed-boost-60-67-tok-s-1m-context-now-with-concurrency/374846?page=5)). One open question could change this picture. OpenRouter's `qwen3.8-flash` and the open-weight Qwen3.8-Flash-Next may or may not be the same model, and sources disagree on whether the hosted Flash is proprietary ([llmreference](https://www.llmreference.com/model/qwen3.8-flash-next/openrouter)). If they are the same weights, the local fallback could match the 93/120 model. But Flash-Next takes a whole Spark (about 122 GiB with patched vLLM), and its author calls it "not a daily driver" ([vitorallo](https://vitorallo.github.io/blog/2026/dgx-spark-coding-models/)). Running the user's 120-prompt agreement harness against it settles the question.

**Mem0 extraction and embeddings.** Scale barely matters here. Extraction models of 0.6-4B built for the task reach 79.6-81.4% on LOCOMO, against Mem0's 64.2% ([MemReader](https://arxiv.org/pdf/2604.07877)). Another paper finds Mem0's aggressive summarization loses more than a better model gains ([ProMem](https://arxiv.org/pdf/2601.04463)). Moving from Qwen3-Embedding-4B to 8B adds only **+1.1 multilingual and +0.6 English MTEB points** ([HF card](https://huggingface.co/Qwen/Qwen3-Embedding-4B)), and it would force a new 4096-dimension collection. Both workloads already fit comfortably on one Spark.

**Coding agents.** This is the only workload where a second box changes quality, and the evidence is mixed on the size of the gain.

The 2-Spark tier also slows down at the context lengths agents use. ## On today's shared box, Qwen3.6-35B-A3B beats Qwen3.8-27B on fit and speed

On paper, Qwen3.8-27B is clearly the better coder. It scores **61.7 vs 49.5** on SWE-bench Pro and **90.3 vs 80.4** on LiveCodeBench v6 ([Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B); [Qwen3.6-35B-A3B](https://huggingface.co/Qwen/Qwen3.6-35B-A3B)). Artificial Analysis shows large gaps on its agentic evals, for example AutomationBench 48.2% vs 5.2% ([Artificial Analysis](https://artificialanalysis.ai/models/comparisons/qwen3-8-27b-vs-qwen3-6-35b-a3b)). NVIDIA's NVFP4 build loses only about 1.5 Terminal-Bench points against BF16 ([nvidia/Qwen3.8-27B-NVFP4](https://huggingface.co/nvidia/Qwen3.8-27B-NVFP4)), and it is the model NVIDIA Sync's launcher installs and wires to OpenCode ([NVIDIA Sync docs](https://docs.nvidia.com/sync/latest/models.html)). If the box had memory and bandwidth to spare, this would be an easy call.

The box has neither. The 27B is dense, so it reads all of its ~24 GB of weights for every token. On a Spark it decodes at **~10-12 tok/s bare and ~18-29 tok/s with MTP** on vLLM, and prefill falls from 1,734 tok/s at 4.6K to 853 tok/s at 48K ([NVIDIA forum 380244](https://forums.developer.nvidia.com/t/qwen3-8-27b-nvfp4-on-a-single-dgx-spark-up-to-1m-context-vllm-mtp-measurements/380244); [NVIDIA forum 381102](https://forums.developer.nvidia.com/t/comprehensive-qwen3-8-27b-study-on-dgx-sparks-quantization-speculative-decoding-and-tp-dp-scaling/381102)). One owner using it from OpenCode saw 15-25 tok/s ([NVIDIA forum 380244](https://forums.developer.nvidia.com/t/qwen3-8-27b-nvfp4-on-a-single-dgx-spark-up-to-1m-context-vllm-mtp-measurements/380244)). The MoE runs at **~100-108 tok/s with MTP** and prefills at 5,300-6,500 tok/s ([Classmethod](https://dev.classmethod.jp/en/articles/dgx-spark-qwen3-6-35b-a3b-nvfp4-new-champion/); [NVIDIA forum 371810](https://forums.developer.nvidia.com/t/benchmark-report-qwen3-6-35b-a3b-nvfp4-on-nvidia-dgx-spark-jetson-thor-blackwell-6000-pro/371810)). Running alongside Nemotron 3.5 Lightning, the arrangement the user has today, the MoE still managed 77.9 tok/s single-stream, while TTFT roughly doubled under shared load ([NVIDIA forum 386489](https://forums.developer.nvidia.com/t/two-models-on-one-dgx-spark-qwen3-6-35b-nvfp4-nemotron-3-5-lightning-with-dspark-numbers-under-shared-load-and-a-fix-for-cudnn-fp8-crashes/386489)). Nobody has measured the 27B under the same contention. Because it reads about 9x more bytes per token, contention should hurt it more.

Memory decides it. The 27B's fixed footprint was measured at **28.1 GiB**, and its fp8 KV costs **37 KB per token**. The MoE's fixed cost is about 25 GiB and its KV about 11 KB per token ([NVIDIA forum 380244](https://forums.developer.nvidia.com/t/qwen3-8-27b-nvfp4-on-a-single-dgx-spark-up-to-1m-context-vllm-mtp-measurements/380244); [NVIDIA forum 371810](https://forums.developer.nvidia.com/t/benchmark-report-qwen3-6-35b-a3b-nvfp4-on-nvidia-dgx-spark-jetson-thor-blackwell-6000-pro/371810)). The research notes' arithmetic from those figures gives the following budgets.

| vLLM share of 121.6 GiB | Qwen3.8-27B context | Qwen3.6-35B-A3B context |
|---|---|---|
| 25% (current) | ~65K, one sequence | ~420K (full 262K fits) |
| 30% | ~240K, one sequence | ~900K |
| 40% (NVIDIA's MoE recipe) | ~580K | ~1.8M |

At the current 25% share, the 27B has room for one ~65K session. OpenCode and Hermes resend system prompts, tool schemas and file contents, so that is tight, and a cold 50K prompt would take about a minute to prefill. Long reasoning makes it worse. At its default `xhigh` effort, Artificial Analysis measured about **110K output tokens per task** ([Artificial Analysis](https://artificialanalysis.ai/models/comparisons/qwen3-8-27b-vs-qwen3-6-35b-a3b)), which at ~25 tok/s is over an hour of decode per heavy task. Using it interactively means dropping to `reasoning_effort: medium`. One owner-reported caveat cuts the other way, and it applies to the previous generation: in Hermes, Qwen3.6-27B "frequently get[s] in to loops" on tests, while the 35B "identified the failure, patched it, and moved on" ([NVIDIA forum 367721](https://forums.developer.nvidia.com/t/for-loacl-agent-qwen3-6-35b-or-qwen3-coder-next/367721)). No one has re-tested this with 3.8.

Two inferences follow from these numbers, and both are cheaper than buying hardware. First, the user's MoE runs at 32K context inside a 25% share whose KV pool, by this arithmetic, would hold over 400K tokens. vLLM preallocates the share, so raising `--max-model-len` to 128K-262K should not add memory pressure. The 2026-11-11 freeze happened outside the fixed vLLM shares: the kernel log shows a global OOM at 17:03 while Qwen3.6 was still loading with `--load-format fastsafetensors` (which stages the checkpoint in host memory) at a 0.30 share, beside Lightning and a concurrent `uv sync`. Restarted with the default loader at 0.25 and 32K, it loaded with available memory never below 50 GB. Owners warn that `docker stats` under-reports GPU memory on a Spark (7.7 GiB shown for a container using 52.9 GiB) and recommend a watchdog on `/proc/meminfo` MemAvailable below 12,000 MiB ([NVIDIA forum 386489](https://forums.developer.nvidia.com/t/two-models-on-one-dgx-spark-qwen3-6-35b-nvfp4-nemotron-3-5-lightning-with-dspark-numbers-under-shared-load-and-a-fix-for-cudnn-fp8-crashes/386489)). The same thread notes that vLLM exits 0 after an EngineDeadError, so the services need systemd `Restart=always`. Second, Nemotron 3.5 Lightning holds 22% of the box and is the weakest trading model the user has measured (67/120). If Qwen3.6-35B-A3B matches it on the agreement harness, it can serve as the local trading fallback too. Retiring Nemotron would then free enough memory to give Qwen3.8-27B a 40%+ share on the existing hardware.

## Two independent Sparks capture most of the gain without the fragility

| Option | Trading / mem0 | Coding model | Main risk |
|---|---|---|---|
| Stay on one Spark | Unchanged (API-led) | Qwen3.6-35B-A3B at 25%, raise context | Memory contention, now known |
| Two independent Sparks | Box A, isolated from coding load | Box B: Qwen3.8-27B at full share (~240K-580K+, MTP; sparkrun measured 39 tok/s and 98 aggregate across 4 lanes), or Flash-Next | Two boxes to maintain |
| Two clustered Sparks | Must share the cluster or a third host | GLM-5.3-Flash / DeepSeek-V4-Flash / Flash-Next TP=2 | Boot time, patches, no failover, concurrency collapse |

The sparkrun figure is from [NVIDIA forum 380244](https://forums.developer.nvidia.com/t/qwen3-8-27b-nvfp4-on-a-single-dgx-spark-up-to-1m-context-vllm-mtp-measurements/380244).

Running the boxes independently solves the problem the user actually has. The latency-sensitive trading path never waits behind a 50K-token coding prefill. Box B can run Qwen3.8-27B with enough memory for multiple long sessions, which is the 12-point vendor SWE-bench Pro step up from today's model. Either box can host the trading fallback if the other dies. One owner on the NVIDIA forum runs this pattern, with a different model on each Spark ([NVIDIA forum](https://forums.developer.nvidia.com/t/best-2026-model-for-agentic-work-on-a-2-node-spark-cluster/369799)). The extra gain from clustering is the gap between Qwen3.8-27B and a 300B-class MoE. That gap is 6-8 tasks on one 40-task run and negative on vendor numbers, and clustering pays for it with all of the operational costs described above.

The economics argue against buying for quality at all. A second unit costs about $6,950 for a DGX Spark or about $5,999 for an ASUS GX10, plus a $159 cable ([physicalailab](https://physicalailab.io/en/nvidia-dgx-spark-price-specs-buy/); [spheron](https://www.spheron.network/blog/dgx-spark-alternatives-dell-asus-hp-lenovo-gb10-compared-2026/); [Petronella](https://petronellatech.com/hardware/connectx-7-qsfp112-dac-cable/)). DeepSeek-V4-Flash-0731, the strongest model in the 2-Spark tier, costs $0.0434 per million input tokens and $0.30 per million output on OpenRouter ([OpenRouter](https://openrouter.ai/deepseek/deepseek-v4-flash-0731)). A heavy agent day of 50M input and 1M output tokens comes to about $2.50, or roughly $900 a year. That is a 7-8 year payback before electricity, and that volume figure is an assumption, not a measurement. Local hardware wins on privacy, isolation, freedom from rate limits and fixed-cost always-on agents. It does not win on tokens per dollar.

## Recommendation

**Do not buy a second Spark to get better models.** Trading quality is set by the API models, mem0 does not scale with model size, and the coding gain is achievable for less. Do three things now, in order. First, raise Qwen3.6-35B-A3B's context from 32K toward 128K-262K inside its existing 25% share, and add the MemAvailable watchdog and `Restart=always`. Second, run Qwen3.6-35B-A3B (and, if its weights are confirmed equivalent, Qwen3.8-Flash-Next) through the 120-prompt Grok-agreement harness. If the MoE scores at least 67/120, retire Nemotron 3.5 Lightning. Third, use the freed memory to move the coding role to **Qwen3.8-27B at a 40%+ share with MTP n=3, fp8 KV and `reasoning_effort: medium`**. If you cannot free that memory, stay on Qwen3.6-35B-A3B: at a 25% share the 27B is too memory-starved and too slow to beat it in practice. **If you buy a second Spark anyway, for isolation, privacy or headroom, run the boxes independently**: trading, mem0 and Postgres on box A, Qwen3.8-27B with the full box on box B. Cable them, but cluster only for an occasional hard task on GLM-5.3-Flash or Qwen3.8-Flash-Next at TP=2.

## Conclusion

What the user is short of is memory isolation, not model capability. Every workload except coding is already at or near its quality ceiling, and the one with the most money at stake, trading, gets its quality from hosted models that cost fractions of a cent per call. The open-weight frontier is also improving faster at the small end than the large end. A 27B dense model matches 300B-class MoEs on vendor coding benchmarks, so the value of 240 GB of clustered memory is shrinking with each Qwen release. The best case for the cluster, one 40-task SWE-bench Pro run, favours Qwen3.8-Flash-Next, a model that fits a single box.

The decisive unknown is cheap to resolve. If OpenRouter's qwen3.8-flash and the open Qwen3.8-Flash-Next weights are the same model, one dedicated Spark could host the 93/120 trading fallback and a top-tier coding model at once. That would be the strongest argument for a second box, and it is an argument for a dedicated one, not a cluster. The user's existing agreement harness can test it before any money is spent.
